# Database Schema & Indexing Strategy

This document details the database architecture of the Tender Compliance Engine, specifying tables, types, constraints, relations, and vector indices.

---

## 1. Storage Backend Selection

The system supports two database backends:
- **SQLite**: Default for local development and unit tests (`llm_eval.db`). It maps the vector embeddings field as a standard serialization `JSON` type and uses Python-level scoring.
- **PostgreSQL (with `pgvector`)**: Recommended for production (deployed serverless on Neon). It uses native `vector` data types, and leverages PostgreSQL-level cosine distance and HNSW (Hierarchical Navigable Small World) indices.

The database mode is resolved automatically at startup:
- If `DATABASE_URL` starts with `postgresql://` or `postgres://`, it registers the connection listener and verifies if the `vector` extension can be initialized.
- If it starts with `sqlite://`, it falls back to local SQLite operations.

## 3. Indexing & Optimization Strategy

To maintain sub-second retrieval times as the corpus of knowledge base files and corporate profiles grows, the system implements a multi-part indexing strategy:

### 3.1 Vector Similarity Indexing (PostgreSQL)
Standard relational databases perform linear scans for vector similarity queries, resulting in `O(N)` search times. The platform configures a **Hierarchical Navigable Small World (HNSW)** index in PostgreSQL for fast approximate nearest neighbor (ANN) searches:

```sql
CREATE INDEX IF NOT EXISTS knowledge_chunks_embedding_hnsw_idx 
ON knowledge_chunks 
USING hnsw (embedding vector_cosine_ops);
```

* **Parameters**:
  - **Operator Class**: `vector_cosine_ops`. Optimizes retrieval based on Cosine Distance: `1 - (A . B / (||A|| * ||B||))`. This is appropriate since embeddings are normalized, isolating lexical relevance from segment length.
  - **Vector Dimension**: Dictated by `Settings.embedding_dimensions` (Default is `12` for local testing vectors, scales up to `1536` for `text-embedding-3-small` in production).

### 3.2 Relational B-Tree Indexing
B-Tree indexes are generated automatically on high-cardinality search columns:
- **`users.user_id`**: For authentication checks and Clerk profile synchronization.
- **`feedback_entries.requirement_id` & `feedback_entries.analysis_id`**: To fetch historical user corrections and match requirements during the compliance analysis stage.
- **`knowledge_chunks.scope` & `knowledge_chunks.content_hash`**: To query within the request-scoped capability boundaries without scanning global default knowledge sets.
- **`document_assets.content_hash`**: To verify if a newly uploaded PDF has already been ingested.
